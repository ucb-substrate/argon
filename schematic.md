# Schematic and symbol entry in the GUI

This is a plan for drawing and editing a cell's schematic and symbol in Argone. The approach is the same as for layout. The GUI never writes files: every gesture becomes a source edit that the analyzer applies through Neovim, and what the GUI shows always comes from the compiled result.

## Decisions

| Topic | Decision |
| --- | --- |
| Drawing data | Placement and wires live in source, as keywords: placement on the call that creates each element, and a wire's corners on the `connect` it draws. |
| Connectivity | Only `connect` calls and device terminal lists connect. The GUI draws the wires the source stores and never routes one itself; a connection without a wire is drawn as a flyline. |
| Symbols | A cell draws its symbol in its body with `std::symbol`, next to its layout and schematic statements. A cell that draws none gets a generated box. Devices are drawn with the `std::symbol` helper for their kind. |
| Devices | Devices become first-class: `device()` returns a handle with named terminals, takes placement keywords, and is named after its binding in netlists. `Nmos`, `Pmos`, `Npn`, and `Pnp` kinds choose a polarity symbol and netlist as `Mos` and `Bjt`. |
| View | Layout, schematic, and symbol are three views of the open cell, toggled in the same window. The symbol view is an editor, like the schematic view. |

These decisions lead to a few working rules:

- The source is the only persistent state. Display preferences such as the camera, flyline visibility, and descend path live in the GUI for the session.
- A gesture is one `workspace/applyEdit`, so it's one Neovim undo step. Neovim keeps undo per buffer, though, so a gesture that edits several files is one step in each of them. Only rename (milestone 8) does that; deletion refuses rather than edit another file (§6.5).
- Inserted code uses full `std::schematic::` and `std::symbol::` paths, so it needs no `use`.
- Every schematic and symbol renders, including ones generated by loops and functions. The GUI can edit an element, a wire, or a symbol item only when one source location corresponds to it alone.
- Placement, routes, and symbols never change netlists, net names, element names, or ports.

## 1. Starting point

**Language.**

- What exists today: `Signal()`, `connect(a, b)`, `device(kind, terminals, model, ..params) -> ()`, and `std::schematic::inst(cell) -> SchematicInst`.
- The compiled form is `CompiledCell.schematic: Schematic { nets, ports, instances, devices, elements }` (`crates/compiler/src/compile/schematic.rs:21`). It's topology only. It has no positions, no span for a `Signal()`, no record of `connect` calls, and no value for a device.
- Netlists are written with `arc run --spice` / `--spectre` (`crates/compiler/src/netlist/mod.rs`).
- **There's no symbol data.** A cell has two views, layout and schematic. The standard library has three modules (`STD_MODULES`, `crates/compiler/src/parse.rs:50`), and `Native::module` (`compile.rs:171`) binds each native in one of them.

**GUI and analyzer.**

- **The schematic already reaches the GUI.** Every snapshot carries `Schematic`, because it's part of `CompiledCell`. That includes cells placed only with `std::schematic::inst`. Nothing in `crates/gui` or `crates/analyzer` reads it yet.
- **`LayoutCanvas` is large and hard-wired in.** It lives in `crates/gui/src/editor/canvas.rs` (about 14.4k lines) and owns tools, painting, raster tiles, hit testing, and SSE. It's tied to the rest of the GUI in several ways:
  - its slot in `Editor` (`editor/mod.rs:141`);
  - the global `ToolState` (`canvas.rs:1170`);
  - the `"LayoutCanvas"` key context;
  - the sidebars;
  - the editor, which routes focus, pointer events, fit, and snapshot gating through it.

  §5.1 lists every site. The hierarchy (`editor/hierarchy.rs`) only follows layout instances.
- **Several pieces can be reused as they are, or nearly:**
  - `insert_statement` and `let_prefix` (`crates/analyzer/src/rpc.rs:268`, `:314`).
  - `update_values` with `InitialConditionEdit` (`rpc.rs:878`). It inserts or rewrites a keyword on a call that it finds by span, which is what moving, rotating, and rerouting need.
  - The `:Argon inst` preview flow (`crates/analyzer/src/lib.rs:1604`) and its completion (`command_completion.rs`).
  - The editing core of `TextInput` (`editor/input.rs`).
  - `SyncLangServerClient::call_async` (`crates/gui/src/rpc.rs:181`). It's private, and the wrappers this plan builds on (`update_values`, `select_rect`, `place_instance`) block the UI thread for up to 10 s. §6.2 adds async variants.
  - The render-test harness (`editor/render_regression.rs`) and the headless full-stack tests (`crates/tests/src/full_stack.rs`).

## 2. Language changes

### 2.1 Placement keywords

```argon
pub let a = Signal(x=-8, y=0);
let nmos = std::schematic::inst(mos(true, nw, nf), x=0, y=-4);
let m0 = device(DeviceKind::Mos, signals(4), "nch", w=1., l=0.15, x=6, y=0, angle=90);
```

| Keyword | Type | Accepted by | Meaning |
| --- | --- | --- | --- |
| `x`, `y` | `Int` | `inst`, `Signal`, `device` | Position of the element's origin, in grid units, with y pointing up. |
| `angle` | `Int` | `inst`, `Signal`, `device` | Counterclockwise rotation in degrees, a multiple of 90. |
| `reflect` | `Bool` | `inst`, `device` | Mirror about the x axis before rotating, as `std::layout::inst` does. |

- **The `x` and `y` pair.** `x` and `y` are given together; one without the other is a static error. `angle` and `reflect` may come without them, and then orient the element wherever the GUI places it.
- **Coordinates are `Int` grid units**, for four reasons:
  - A schematic lives on a grid.
  - The indices from `std::range` are `Int`, so `x=4 * i` works inside a loop.
  - The literals stay short.
  - An `Int` never waits on the solver, so placement can't hold up evaluation.

  Layout coordinates stay `Float`. So `x=0.` on a schematic call gets a targeted diagnostic: "schematic coordinates are grid units; write `x=0`".
- **`angle` is normalized** as layout normalizes it: `450` means `90` and `-90` means `270`. A value that isn't a multiple of 90 is `ExecErrorKind::InvalidRotation`.
- **Pin or label.** A placed signal is drawn as a port pin when a `pub` field reaches that signal, and as a net label otherwise. A label shows its net's name. Two placed public signals on one port are drawn as two pins of that port.
- **Signals created in functions.** A `Signal(x=…, y=…)` inside a `fn` places the signal of every call at the same point. A function that creates signals should take positions as parameters, or leave them out.
- **Reserved device keywords.** On `device`, `x`, `y`, `angle`, and `reflect` stop being netlist parameters. Netlist parameters ignore case, so `X`, `ANGLE`, and so on are rejected rather than passed through. Code that passes one of these names as a parameter today will break, and the docs need to say so.
- **Placement can't be read back.** A schematic instance still has no `x` or `y` field. That keeps presentation out of evaluation, so placement can't change a netlist.

### 2.2 Routes

`connect` takes a `route` keyword: the corners of the wire that draws the connection.

```argon
connect(a, mp.g, route=[(-4, 0), (-4, 4)]);
connect(vdd, mp.s, route=[]);
connect(x, y);
```

- **Ends come from pins.** The wire runs from the pin of the first signal, through the corners in order, to the pin of the second (§4.3). A route never stores its ends, so when an element moves, whether by a gesture or a hand edit, its wires' ends move with its pins.
- **Absent or empty.** `route=[]` is a straight wire between the two pins. A `connect` without `route` draws no wire, so unless other wires join its ends, the GUI shows it as a flyline (§4.4).
- **The type is `[(Int, Int)]`,** in grid units, as placement is. So `route=[(4 * i, 6)]` works in a loop, and a route never waits on the solver. A `Float` corner gets the grid-unit diagnostic.
- **Segments** are straight lines between consecutive points. Hand-written routes may have diagonal segments; the GUI writes only horizontal and vertical ones.
- **Only `connect` draws wires.** A device's terminal list joins its pins to signals without drawing anything. So the GUI gives a new device fresh signals and draws its wires with `connect` calls to its terminals (§2.4).
- **Can't be read back.** `connect` still returns `()`, so a route, like placement, can't change a netlist.

### 2.3 Device handles

`device(...)` returns a `Device`, whose fields are its terminals:

| Kind | Fields |
| --- | --- |
| `Mos`, `Nmos`, `Pmos` | `d`, `g`, `s`, `b` |
| `Res`, `Cap`, `Diode` | `p`, `n`; a diode's `p` is its anode |
| `Bjt`, `Npn`, `Pnp` | `c`, `b`, `e`, plus `sub` with 4 terminals |
| `Subckt` | none by name |
| every kind | `terminals: [Signal]`, in order |

```argon
let m0 = device(DeviceKind::Nmos, signals(4), "nch", w=1., l=0.15);
connect(m0.g, a);
connect(m0.d, out);
```

- **Polarity kinds.** `DeviceKind` gains `Nmos` and `Pmos`, which are `Mos` devices, and `Npn` and `Pnp`, which are `Bjt` devices. Each takes the same terminals and writes the same netlist element (`M` or `Q`) as its base kind; they differ only in their symbols (§4.1). `Mos` and `Bjt` stay, with generic symbols.
- **What a field reads.** A field reads the device's terminal: a signal of the cell that sits on that pin and is joined to the signal passed at that position. So `connect(m0.g, x)` joins `x` to the gate's net, and a route on that `connect` ends at the gate pin. An instance's terminals work the same way. If fields read the passed signal instead, a wire couldn't name either pin of two devices that share a signal.
- **One type for every kind.** `Device` can be written in source: `use std::schematic::Device;`, `fn nmos(…) -> Device`. Statically, every name in the table has type `Signal`, and `terminals` has type `[Signal]`. Evaluation checks the name against the device's kind, so `r.g` on a resistor is a run-time error.
- **When the handle is ready.** The handle is ready as soon as `kind` and `terminals` are. A `Float` parameter that waits on the solver delays only the device's parameters, never the `connect` calls that go through its terminals.
- **Net names.** Nets get names through a handle the way they do through an instance: the drain of `let m0 = device(…)` is `m0_d`, unless a better name exists. Without this rule, the fresh signals the GUI writes would fall through to names like `net3`, which shift whenever a net is added.
- **Device names.** A device's element name comes from its binding, as an instance's does: `let mp = device(…)` is `Mmp` in netlists. A device that no binding reaches keeps today's name, its kind's letter and its position among the cell's devices (`R2`). So deleting a device doesn't rename the others, and the netlist uses the names the GUI shows.
- **A `Device` behaves like a schematic instance:**
  - A device's terminal is never a port by itself, even when a `pub let` holds the device.
  - A parent that reads a device through `std::schematic::inst` gets the terminals on ports as its own signals, and the other terminals as detached values.
  - Read through `std::layout::inst`, the whole device is detached.
  - A device can't be a cell argument. If an `Any`-typed cell argument holds one, the cell is rejected when it runs, as it is for signals (`SignalCellArgument`).
  - A device can't be compared, emitted, or used in arithmetic.
- **Existing code is unaffected**, except devices that pass `x`, `y`, `angle`, or `reflect` as parameters. A `device(...);` statement simply drops the handle. Since `device` returns `()` today, no existing device is held by a binding, so no netlist name changes.

### 2.4 `std::schematic::signals`

A new device starts with fresh signals on its terminals:

```argon
fn signals(n: Int) -> [Signal] {
    if n == 0 {
        []
    } else {
        cons(Signal(), signals(n - 1))
    }
}
```

- **It compiles.** I compiled this as a user `fn` against the current compiler.
- **It also works inside `std/schematic.ar`.** There, the bare `Signal()` resolves too: `bind_natives` (`compile.rs:3431`) binds a std module's natives within that module, which is how `std/layout.ar` calls `rect`.
- **How the GUI uses it.** The GUI writes `std::schematic::signals(4)` for a new MOS device of any kind. Its wires are `connect` statements to the device's terminals, which carry the routes (§2.2), so the GUI never needs to edit the terminal list. The fresh signals have no pins of their own, so they draw nothing.
- **Hand-written code** can keep passing named signals where that reads better.

### 2.5 Example

A device-level inverter, placed and wired. Deleting its placement and route keywords leaves its netlist byte-identical.

```argon
use std::schematic::{DeviceKind, Signal, connect, device, signals};

cell device_inv(pw: Float, nw: Float) {
    pub let a = Signal(x=-6, y=0);
    pub let out = Signal(x=4, y=0);
    pub let vdd = Signal(x=0, y=8);
    pub let vss = Signal(x=0, y=-8);

    let mp = device(DeviceKind::Pmos, signals(4), "pch", w=pw, l=0.15, x=0, y=4);
    let mn = device(DeviceKind::Nmos, signals(4), "nch", w=nw, l=0.15, x=0, y=-4);

    connect(a, mp.g, route=[(-4, 0), (-4, 4)]);
    connect(a, mn.g, route=[(-4, 0), (-4, -4)]);
    connect(out, mp.d, route=[(0, 0)]);
    connect(out, mn.d, route=[(0, 0)]);
    connect(vdd, mp.s, route=[]);
    connect(vdd, mp.b, route=[(2, 8)]);
    connect(vss, mn.s, route=[]);
    connect(vss, mn.b, route=[(2, -8)]);
}
```

- **Symbols.** With the symbols of §4.1, `mp`'s pins are `s` (0, 6), `g` (-2, 4), `d` (0, 2), and `b` (2, 4); the `Pmos` symbol has its source on top, facing `vdd`. `mn`'s pins are `d` (0, -2), `g` (-2, -4), `s` (0, -6), and `b` (2, -4).
- **Shared segments.** The two `a` wires share the segment from (-6, 0) to (-4, 0). It's drawn once, with a junction dot at (-4, 0). The two `out` wires meet at (0, 0) the same way.
- **Nothing else is drawn.** Every net is fully wired, so there are no flylines.

### 2.6 Symbols

A cell draws its symbol with `std::symbol` calls in its body, next to its layout and schematic statements. One run of the body produces all three views, so a symbol can depend on the cell's parameters. A parent's schematic draws each instance of the cell with this symbol (§4.1).

The inverter of §2.5, with a symbol:

```argon
use std::symbol::{circle, inst_name, line, param, pin, polygon};

cell device_inv(pw: Float, nw: Float) {
    // Ports, devices, and connections as in §2.5.

    polygon([(-2., 2.), (-2., -2.), (2., 0.)]);
    circle(x=2.25, y=0., r=0.25);
    line([(-4., 0.), (-2., 0.)]);
    line([(2.5, 0.), (4., 0.)]);
    line([(0., 1.), (0., 4.)]);
    line([(0., -1.), (0., -4.)]);

    pin(a, x=-4, y=0);
    pin(out, x=4, y=0);
    pin(vdd, x=0, y=4, label=true);
    pin(vss, x=0, y=-4, label=true);

    inst_name(x=2., y=2.);
    param("pw", pw, x=2., y=-2.);
    param("nw", nw, x=2., y=-3.);
}
```

**The natives.** Each returns `()`. Coordinates are keywords and are required. `size` and `align` are optional on `text`, `inst_name`, and `param`.

| Call | Draws |
| --- | --- |
| `line(points)` | An open polyline through two or more points. |
| `polygon(points, fill=false)` | A closed outline through three or more points. |
| `rect(x0=, y0=, x1=, y1=, fill=false)` | An axis-aligned rectangle. |
| `circle(x=, y=, r=, fill=false)` | A circle. |
| `arc(x=, y=, r=, start=, end=)` | An arc running counterclockwise from `start` to `end`, in degrees from the +x axis. |
| `text(value, x=, y=)` | Literal text. |
| `inst_name(x=, y=)` | The instance's name in the parent, such as `Xinv` or `Mmp`. |
| `param(name, value, x=, y=)` | `name=value`, with `value` formatted as netlists format parameters (`w=0.15`, `c=1e-12`). |
| `pin(signal, x=, y=, label=false)` | The pin of the port that `signal` is on, where a parent's wires end. With `label=true`, the port's name is drawn beside it. |

- **Types.** `points` is `[(Float, Float)]`. Shape and text coordinates, `r`, `start`, `end`, and `size` are `Float`. Pin coordinates are `Int`. `fill` and `label` are `Bool`. `align` is a `std::symbol::Align`: `Left` (the default), `Center`, or `Right`. `param`'s `value` is a `Float`, `Int`, or `String`, typed as device parameters are.
- **Units.** Everything is in grid units. Pins are `Int`, so they sit on the grid and a parent's wires end on grid points. Shapes and text are `Float`, so arrows, bubbles, and arcs can fall between grid points. A `Float` pin coordinate gets the grid-unit diagnostic of §2.1.
- **Values must be numbers.** A `Float` that depends on constraints waits until it's solved, as a device parameter does. A value that never solves or isn't finite is an execution error. So are a `line` with fewer than two points, a `polygon` with fewer than three, and an `r` or `size` that isn't positive.
- **Text.** `size` is the text height, 1 by default. Text runs horizontally in symbol coordinates and is centered vertically on `y`; `align` says whether `x` is its left end, its center, or its right end. The GUI keeps text upright under every placement (§4.1). `inst_name` and `param` are placeholders, because the instance's name is known only in the parent, and Argon has no string concatenation.
- **Pins.**
  - A pin names a port through any signal on that port's net, the way `connect` names a net. When `connect(a, m.g)` has joined them, `pin(a, …)` and `pin(m.g, …)` name the same port.
  - Pins are checked once the body has run and the ports are known. Each of these is an execution error:
    - a `pin` on a net that isn't a port;
    - two pins for one port, since a parent's route has to end at one pin;
    - two pins at one point;
    - a port without a pin, in a cell that draws a symbol. The error points at the `pub let` that made the port.
  - A cell with errors still has the rest of its symbol drawn. A port without a pin gives its terminals nowhere to draw a wire to (§4.3).
  - A symbol pin is separate from a placed signal in the cell's own schematic (§2.1). One says where the port is on the symbol, and the other says where the port is drawn inside the cell.
- **Pin labels.** `label=true` draws the port's name at size 1, beside the pin and clear of a stub of any length. The pin's side is the nearest edge of the bounding box of the symbol's shapes, with left and right winning ties; a symbol without shapes uses its pins' bounding box. The name goes here:

  | Side | Position | Alignment |
  | --- | --- | --- |
  | Top | (x + 0.5, y - 1) | `Left` |
  | Bottom | (x + 0.5, y + 1) | `Left` |
  | Left | (x + 0.5, y + 1) | `Left` |
  | Right | (x - 0.5, y + 1) | `Right` |

  In the inverter above, `vdd`'s name is at (0.5, 3). A label follows the shapes, so a shape that changes which edge is nearest moves it to another side.
- **Which cells have symbols.** A cell draws a symbol when it makes at least one `std::symbol` call, directly or through a function. A cell that makes none gets the generated box of §4.1.
- **Functions.** A `std::symbol` call inside a function draws in the cell that called the function, as `Signal()` creates a signal there. So symbols can be shared as functions, and the device helpers below are ordinary Argon.
- **Names.** `rect`, `polygon`, and `text` also exist in `std::layout`, as `inst` exists in both `std::layout` and `std::schematic`. Import one under an alias, or call it by path. A bare `rect` that doesn't resolve still reports that it moved to `std::layout`, because `Native::named` only searches `std::layout`.
- **Can't be read back.** A symbol is only presentation. Nothing in evaluation reads it, it isn't reachable through an instance, and a parent's symbol doesn't include its children's. Deleting every `std::symbol` call leaves netlists byte-identical.

**Device helpers.** `std/symbol.ar` draws the device symbols as Argon functions over the natives. Each one draws its shapes, its pins, and `inst_name`.

| Helper | Pins |
| --- | --- |
| `mos(d, g, s, b)`, `nmos(d, g, s, b)` | `d` (0, 2), `g` (-2, 0), `s` (0, -2), `b` (2, 0) |
| `pmos(d, g, s, b)` | `s` (0, 2), `g` (-2, 0), `d` (0, -2), `b` (2, 0) |
| `res(p, n)`, `cap(p, n)`, `diode(p, n)` | `p` (0, 2), `n` (0, -2) |
| `bjt(c, b, e)`, `npn(c, b, e)` | `c` (0, 2), `b` (-2, 0), `e` (0, -2) |
| `pnp(c, b, e)` | `e` (0, 2), `b` (-2, 0), `c` (0, -2) |
| `bjt4`, `npn4`, `pnp4` | The pins of the 3-terminal helper, plus `sub` (2, 0). |

- **Wrapper cells.** A cell that wraps one device can draw itself as that device. The `mos` cell of the schematic docs does it by adding this to its body:

  ```argon
  if nfet {
      std::symbol::nmos(d, g, s, b);
  } else {
      std::symbol::pmos(d, g, s, b);
  }
  ```

- **Raw devices** are drawn with the helper for their kind and terminal count (§4.1), so a wrapper cell and the device it wraps look the same.
- **Module order.** `std::symbol` comes after `std::schematic` in `STD_MODULES`, since the helpers take `Signal`s. `Align` is an ordinary enum in `std/symbol.ar`.

## 3. Compiler changes

### 3.1 Typing

All in `crates/compiler/src/compile.rs`:

- **`inst` keywords.** `builtin_sig::SCHEMATIC_INST` (`:2331`) gains `x`, `y`, and `angle` as `Int` and `reflect` as `Bool`.
- **`Signal` keywords.** `Native::Signal` (`:4537`) is checked against a new signature with `x`, `y`, and `angle`, instead of `NONE`.
- **`connect` keyword.** `builtin_sig::CONNECT` (`:2328`) gains `route` as `[(Int, Int)]`.
- **`device` keywords and type.** `typecheck_device_params` (`:4575`) types the four placement names, rejects their case variants, and treats every other keyword as a parameter. `Native::Device` returns `Ty::Device`. That type doesn't carry the kind, so it needs no new rules in `unify` (`:4107`), whose fallback compares types for equality.
- **`Ty::Device` fields.** Every terminal name in §2.3 has type `Signal`, and `terminals` has type `[Signal]`.
- **Where signals are rejected, devices are too.** `signal_path` (`:4606`), which keeps signals out of cell parameters, gets a `Ty::Device` arm, as do operators, comparisons, and `!`.
- **New static checks:** the `x`/`y` pair, and the diagnostic for a `Float` coordinate in a placement or a route.

### 3.2 Evaluation

- **`Native::Signal`** (`:11678`): record the call span and placement on the new node.
- **`Native::Connect`** (`:11692`): record both nodes, the call span, and the route.
- **`Native::Device`** (`:11717`) and `device_record` (`:10364`). Today the arm stores a value only once the whole record is ready, and reports not-ready while a parameter waits on the solver. The arm splits into two steps:
  1. When `kind` and `terminals` are ready:
     - check the terminal count;
     - create the device's terminal nodes, each joined to the signal passed for it;
     - record the placement;
     - when `terminals` is a list literal, record each terminal expression's span;
     - store a `Value::Device`.
  2. When the parameters are ready, finish the record.

  The device keeps the creation-order position it got in step 1, so naming doesn't change.
- **`Native::SchematicInst`** (`:11742`): read placement with `typed_int` and `typed_bool`, as `std::layout::inst` does (`:11542`–`:11600`).
- **The device value.**
  - Add `Value::Device(Arc<DeviceValue>)` and `FieldValue::Device`.
  - Add arms in `LayoutReader` (`:13805`) and `SchematicReader` (`:13863`) that read a device through an instance.
  - Add `DetachedKind::Device` (`compile/schematic.rs:185`).
- **Naming.** The `walk` in `compile/schematic.rs` treats a device like an instance. Its terminals get tier-2 names (`m0_d`), and a device never makes ports. Its element name comes from its path or name hint, as an instance's does (`:536`), with the kind's letter in place of `X`; without either, it keeps the letter and position (`:546`).
- **Polarity kinds.** `DeviceKind` (`compile/schematic.rs:85`) and the enum in `std/schematic.ar` gain `Nmos`, `Pmos`, `Npn`, and `Pnp`. A new `DeviceKind::base` maps them to `Mos` and `Bjt`, and `letter`, `check`, and the terminal names go through it. The netlist's device body (`netlist/mod.rs:148`) stores the base kind, so subcircuits that differ only in polarity kind still merge.
- **Digest and artifact.** `hash_schematic` (`:14012`) also hashes placement and routes, so `ARGON_VERIFY_CELL_CACHE` still checks what the GUI draws. Bump `MAGIC` in `artifact.rs` in milestone 1, since the serialized `Schematic` changes there.

### 3.3 Compiled schematic

The GUI needs the connectivity graph, not just the nets. With it, the GUI can draw each wire from its `connect`, find the pins of each net for flylines, and map every element and wire back to a statement:

```rust
pub struct Schematic {
    // nets, ports, instances, devices, elements: as today
    /// Every node: a `Signal()` the cell created, or a terminal of one of its instances or devices.
    pub nodes: Vec<Node>,
    /// Every `connect` that ran, in evaluation order.
    pub connections: Vec<Connection>,
    /// Paths into the cell's values, sharing prefixes (see 3.4).
    pub paths: Vec<PathNode>,
    /// The path of each port, relative to an instance of the cell.
    pub port_paths: Vec<Option<PathId>>,
}

pub struct Node {
    pub net: NetIdx,
    pub source: NodeSource,
    pub path: Option<PathId>,
}

pub enum NodeSource {
    Signal { span: Span, placement: Option<Placement>, editable: bool },
    Terminal { instance: usize, port: usize },
    DeviceTerminal { device: usize, terminal: usize },
}

pub struct Connection {
    pub nodes: [NodeIdx; 2],
    pub span: Span,
    /// The corners of its wire, when the call has a `route`.
    pub route: Option<Vec<(i64, i64)>>,
    pub editable: bool,
}

pub struct PathNode {
    pub parent: Option<PathId>,
```

- `editable: bool`
- `path: Option<PathId>`
- `terminal_nodes: Vec<NodeIdx>`: the nodes on its pins.

`Device` also gains `attached_nodes: Vec<NodeIdx>`, the node passed for each terminal, and `terminal_spans: Vec<Option<Span>>`.

### 3.4 Paths

A path is how the GUI names something in code it inserts, such as `connect(a, mos0.g)`.

- **Where paths come from.** Paths come from the final top-level bindings (`state.fields`, `compile.rs:9167`). So they're valid at the end of the cell body, which is where the GUI inserts code.
- **Segments.** A value that's only reachable inside an enum payload has no path.
- **A separate walk.** The naming `walk` (`compile/schematic.rs:668`) can't produce these segments as it is: it uses one `Segment::Index` for both sequence and tuple elements, and it descends into enum payloads. So paths need their own segment kinds.
- **Storage.** Paths go in a per-cell table of path nodes with parent links, so paths that share a prefix share storage. Nodes and elements store a `PathId`, and the GUI renders a path as text only when it writes code. Stored as strings, the paths would add megabytes to each update for loop-generated schematics with around 10^5 nodes.
- **Terminals.** An instance terminal's path is the instance's path followed by the child's port path. A device terminal's path is the device's path followed by `.d`, `.g`, and so on.
- **Port paths** follow the same ranking as port names. For example, `pub let data = [a, Signal()]` has the port `data_1`, whose path is `data[1]`.

### 3.5 Editability

A site is editable when all three of these hold:

1. **Its call is in the cell's own body.** The call has to be inside the span of the root scope, and not in a `fn`, in `std`, or in a `for` body. A loop body is excluded even if the loop ran once, because a position written there is shared as soon as the loop runs twice.
2. **That call produced only this element or connection** in this cell.
3. **Its placement and route keywords are absent or literals:** an `Int` literal, possibly negated, a `Bool` literal, or a list of tuples of `Int` literals.

The GUI draws locked elements and wires as locked, and auto-places locked elements that have no placement. The properties panel shows why each one is locked (§5.5).

### 3.6 Span rebasing

- **What rebasing does.** The incremental compiler reuses cells across edits and moves their spans with `CompiledCell::rebase_spans` (`:14147`) and `FieldValue::rebase_spans` (`:13695`).
- **New spans to rebase:**
  - `Signal()` and `connect` spans;
  - terminal spans;
  - the spans inside `FieldValue::Device`.
- **One pattern needs fixing.** The `Schematic` destructuring there names every field, so new fields won't compile until they're handled. But the `Device { span, .. }` pattern would silently skip `terminal_spans`, so it should name its fields too.
- **Test.** Edit text above a cached cell and check the spans.

### 3.7 Symbols

- **Module.** `parse.rs` adds `STD_SYMBOL_PATH` and a fourth `STD_MODULES` entry, `std::symbol`, after `std::schematic`. Its source is `crates/compiler/src/std/symbol.ar`: `Align` and the device helpers.
- **Natives.** `Native` (`compile.rs:139`) gains one variant per call in §2.6, bound in `std::symbol`. Each gets a `builtin_sig` whose coordinates are required keywords. `param`'s `value` reuses the parameter typing in `typecheck_device_params` (`:4575`).
- **Evaluation.** Each native appends an item to the cell's symbol once its arguments are ready, so items keep call order. `pin` records its signal's node. Once the body has run, those nodes are resolved to ports, the pin checks of §2.6 run, and each pin label is placed by the rule of §2.6.
- **Origins.** A function's exec scope (`create_exec_scope`, `:9688`) also records its call span. For an item drawn inside a function, evaluation walks up the scope's dynamic parents to the call in the cell's root scope that the item ran under. That call is the item's origin.
- **Editability.** The rules of §3.5 apply to each item and pin. Literals also include `Float` literals, `String` literals, `Align` variant paths, and lists of tuples of `Float` literals. The signal of `pin` and the value of `param` are never rewritten, so they can be any expression. A group of items with one origin can be deleted when the origin is a whole statement in the cell's body.

The compiled form:

## 4. Drawing model

`crates/gui/src/editor/schematic/scene.rs` is a pure function from `(&CompiledData, CellId, &DisplayPrefs)` to a `Scene`. A `Scene` holds symbols, pins, labels, wires, junctions, conflict markers, and flylines, all in grid units. It uses no gpui types, so it can be unit tested.

It runs as a background task, keyed by the snapshot revision, the cell on screen, and the display preferences. So descending or hiding flylines rebuilds it without waiting for a snapshot. (`prepare_compilation_snapshot`, `editor/mod.rs:347`, only captures its context when a snapshot arrives.)

### 4.1 Symbols

- **Cell instances** are drawn with their cell's symbol (§2.6), under the instance's placement. The pin of each terminal is the symbol's pin for that port.
- **The generated box.** A cell that draws no symbol gets a generated box. `generated_box` (§3.7) builds it, so the GUI and Create Symbol agree. The pins are the cell's ports, in port order:
  - names that look like supplies (`vdd*`, `vcc*`, `vpwr`, `vpb`, `avdd`, `dvdd`) go on top;
  - names that look like ground (`vss*`, `gnd*`, `vgnd`, `vnb`, `agnd`) go on the bottom;
  - the rest are split in order between the left and right sides, with the first half, rounded up, on the left.

  The origin is the box's top-left corner. Left and right pins run down from y = -2 in steps of 2, at x = 0 and x = w. Top and bottom pins run right from x = 2 in steps of 2, at y = 0 and y = -h. The width w is 2 more than twice the larger of the top and bottom counts, and the height h is 2 more than twice the larger of the left and right counts; each is at least 4.

  The text is fixed as well, and never changes the box's size:
  - the instance name at (0, 1) and the cell name at (0, -h - 1), both left-aligned;
  - each pin's name half a unit inside the box: left-aligned at x = 0.5 for left pins, right-aligned at x = w - 0.5 for right pins, and centered at y = -1 and y = -h + 1 for top and bottom pins.
- **Devices** are drawn with `device_symbol` (§3.7): the symbol of the helper for their kind and terminal count.

  | Kind | Helper |
  | --- | --- |
  | `Mos`, `Nmos`, `Pmos` | `mos`, `nmos`, `pmos` |
  | `Res`, `Cap` | `res`, `cap` |
  | `Diode` | `diode` |
  | `Bjt`, `Npn`, `Pnp` | `bjt`, `npn`, `pnp`, or `bjt4`, `npn4`, `pnp4` with 4 terminals |
  | `Subckt` | None. A generated box with numbered pins split between the left and right sides, showing the model name. |

  The pins are those in the table of §2.6. Key parameters are printed beside a device's symbol, for example `w=1 l=0.15`, since a helper doesn't know them.
- **Text.**
  - `inst_name` shows the element name (`Xinv`, `Mmp`), a pin label the child's port name, and `param` its formatted value.
  - Text is never drawn upside down or mirrored. Under a placement that would do that, the text's anchor moves with the placement, and its alignment flips so it still reads left to right. Under a 90° or 270° rotation, text runs bottom to top.
- **Ports** are drawn as pin glyphs with their names, and **net labels** as tags with their net's name.
- **GDS-imported cells** have no schematic, so an instance of one is a box without pins.
- **Pins** sit on integer grid points in every orientation, so wires meet on the grid.
- **Size.** A symbol's size, for auto-placement (§4.2) and for the boxes drawn when zoomed out, is the bounding box of its shapes and pins. Text is left out.
- **Pin positions are part of the source format.** Stored routes end at pins. So moving a pin in a child's symbol, or changing the generated box rules, moves the wire ends of existing drawings in every parent. The wires stay attached, but their end segments can turn diagonal (§4.3).

### 4.2 Auto-placement

- **Placed elements** are drawn where they're placed.
- **Fixed slots.** An unplaced instance or device goes to slot *k* of a grid anchored at the origin. Here *k* is its creation index among the cell's instances and devices. The grid has 8 columns, and its pitch is the size of the largest symbol, rounded up to a multiple of 4 units.
- **Stability.** The slot depends only on the creation index. So placing or dragging one element leaves a hole instead of moving the others. An unplaced element moves only when its creation index changes, or when the largest symbol crosses a 4-unit size step.
- **Ports.** Unplaced ports form fixed columns to the left and right of the grid, in port order, by the box-symbol side rule.
- **Overlaps.** A placed element can overlap a slot. Hit testing cycles through overlapping elements.
- **Fix positions** writes the current position of every unplaced, editable element in one edit. From then on, nothing moves unless the user moves it.
- **Wiring fixes positions.** A wire gesture that touches an unplaced, editable element or port also writes that element's position. So a slot change never moves the end of a stored wire, except on a locked element, whose wires follow its slot.

### 4.3 Wires

The GUI draws exactly the wires the source stores. It never routes one itself.

- **One wire per routed `connect`.** A `connect` with a `route` is drawn as a polyline from the pin of its first signal, through the corners, to the pin of its second.
- **The pin of a signal:**
  - an instance or device terminal sits on its pin;
  - a placed signal sits at its port pin or label;
  - an unplaced port sits at the pin that auto-placement gave it;
  - an unplaced internal signal has no pin. A route that ends at one isn't drawn, and the properties panel of its net says why;
  - a terminal on a port that has no pin in the child's symbol has no pin either, with the same result. Its flylines end at its element's origin.
- **Touching.** Two items of one net touch when they share a grid point: a pin or label on a segment, two pins or labels at one point, or a segment end on another segment. Segments that cross without either one ending there don't touch. So a port pin or label placed on a pin needs no wire.
- **Overlaps.** Overlapping collinear segments of one net are drawn as one.
- **Branches.** A wire that starts or ends on another wire connects to that wire's nearer end. Its route repeats the other wire's corners from the branch point to that end, and the shared part is drawn once.
- **Junctions.** Once overlaps are merged, a dot marks every point where three or more segment ends of one net meet, and every point where a segment ends inside another segment of its net.
- **Conflicts.** Where items of different nets touch or overlap, the drawing shows a connection that the netlist doesn't have. The GUI draws a marker there and lists it in the properties panel. The netlist is unaffected.
- **Moved pins.** A wire's ends follow its pins. After a hand edit moves an element, its wires stay attached, but an end segment turns diagonal where the route no longer lines up. A move in the GUI rewrites the routes so they stay orthogonal (§7).
- **Selection.** Clicking a wire selects its `connect`. Where routes overlap, repeated clicks cycle through them, as layout's Cmd-click does.

### 4.4 Flylines

A connection that no wire draws is shown as a flyline: a thin dashed straight line that can't be mistaken for a wire.

- **Islands.** The pins, labels, and wires of a net that touch one another form an island. A net with one island is fully drawn.
- **The tree.** A net's flylines form the shortest tree that joins its islands. Each one runs between the nearest pins or labels of the two islands it joins.
- **Names join islands.** Islands that show the net's name, with a port pin or a label, count as joined already, so a label connects by name as it does on paper.
- **Where they appear.** A `connect` without a route and a device's terminal list join nets without drawing anything. Each leaves flylines until wires or labels join the islands.
- **Wiring a flyline.** With the wire tool, hovering a flyline previews a wire with one corner between its two pins, `/` flips the corner, and a click writes it (§7).
- **Hiding.** View → Flylines hides them for the session.

### 5.1 Views

### 5.3 State

- **The cell on screen.** `EditorState` keeps a root path: the steps from the open cell to the cell on screen. Each step names an instance by its schematic element name or its layout scope path. All three views show that cell, so "three views of the open cell" still holds after descending.

- **`SchematicView`** holds the selection, the tool, the camera, flyline visibility, and pending edits. **`SymbolView`** holds the same for the symbol view, without flylines.

### 5.5 Sidebars

- **Left sidebar.**
  - A schematic tree built from `schematic.instances[].cell`, with devices as leaves.
  - A net list, ports first.
  - A click selects an item and zooms to it, a double-click descends, and selecting a net highlights it.

- **Symbol view.**

### 5.6 Pending edits

- **Snapshots are never held back.** The layout's `accepts_snapshot` (`canvas.rs:11318`) rejects whole snapshots while it persists a drag. The schematic doesn't copy this: `solved_cell` is shared, so rejecting a snapshot would also freeze the layout view and the sidebars.
- **An overlay instead.** The schematic canvas draws pending placements and routes on top of each snapshot it accepts:
  - A moved element or wire stays where it was put, and a new one shows as a ghost, until the first snapshot whose revision is at least the one the edit's RPC returned.
  - A failed RPC drops the overlay at once, so an undo or a refused edit never leaves a stuck ghost.
- **One gesture at a time.** Editing tools pause until the previous edit's RPC returns.

### 5.7 Errors and empty states

- **Static errors.** As today, the GUI keeps drawing the last good snapshot under the compile-error banner. Schematic editing is disabled until a snapshot at the published revision arrives; the analyzer would refuse the edits anyway (§6.1).
- **Execution errors with output.** The partial schematic is drawn, without the elements and connections that didn't evaluate, and editing works.
- **Empty views.**
  - A cell with no schematic shows a hint in the schematic view: "No schematic yet: press `p` to add a port or `i` to place an instance".
  - A schematic-only cell shows a hint in the layout view.
  - Fit on an empty view leaves the camera where it is.
- **GDS-imported cells** have no schematic and are read-only.
- **Other files.** Descending into a cell declared in another file sends edits to that file. `apply_source_edit` focuses that file's buffer, as it does for layout.

### 5.8 The symbol view

- **What it shows.** The symbol view shows the symbol of the cell on screen at its origin, over the grid, with a mark at the origin.
  - Each pin is drawn with its port's name, even without `label=true`, so a pin can always be identified.
  - `inst_name` shows the instance name of the last descend step, or `X?` at the top cell.
  - `param` shows the value the cell on screen was compiled with.
- **Generated symbols.** A cell that draws no symbol shows its generated box, locked, with a Create Symbol button. The drawing tools are disabled until it's used. Create Symbol writes the box as `std::symbol` calls with the same pins (§6.2), so parents' wires stay where they are, and the box becomes editable. The pins get `label=true`, so their names move by about a unit, to the positions of §2.6.
- **Errors.** Ports without pins are marked in red in the left sidebar's port list, since they have no position on the canvas. Other pin errors are marked at the pins concerned.

## 6. Analyzer and RPC

### 6.1 Edit safety

**The current guard misses two cases.** The guard, `editor_buffers_are_current` (`rpc.rs:248`), lets an edit through in two cases where the GUI's spans can be stale:

- **While an earlier edit is pending.** A file with `pending_workspace_edits` counts as current until its `didChange` arrives.
- **After a compile with static errors.** `publish_compilation` (`lib.rs:900`) advances the published AST, but the GUI keeps showing its previous snapshot.

Exact `span2call` and `span2scope` lookups mostly fail safe in those cases. But finding a statement by containment, which deletion has to do, doesn't.

**Every schematic edit therefore follows four rules:**

- **It carries `base_revision`:** the revision of the snapshot the GUI drew the gesture on. The edit is refused unless `base_revision` equals the published revision and no file the edit touches has pending edits.
- **It returns an `EditReceipt { revision, spans }`,** like `RectangleEditResult` (`rpc.rs:89`). The GUI uses it to retire its overlay (§5.6).
- **It resolves every span as an exact `span2call` key** whose callee is the expected native, such as `std::schematic::connect` or `std::symbol::line`, or for a group, a function. It never resolves a span by containment.
- **It parses every path the GUI sends** as an expression before splicing it in.

The same guard could later protect the layout tools.

### 6.2 New `LangServer` methods

Each of these methods follows the same steps:

1. It takes the root scope span of the cell on screen.
2. It runs the usual guards, plus the checks in §6.1.
3. It inserts code with `insert_statement` and applies a single `WorkspaceEdit`.

| Method | Effect |
| --- | --- |
| `add_signal(cell, name, port, at, connect_to, route)` | `pub let` (for a port) or `let` (for a label): `name = std::schematic::Signal(x=…, y=…);`. Given a path, it also adds a `connect`, with a route when the gesture drew one. |
| `place_schematic_instance(cell, invocation, at)` | `pub let mos0 = std::schematic::inst(<invocation>, x=…, y=…);` |
| `place_device(cell, kind, count, args, at)` | `pub let nmos0 = std::schematic::device(std::schematic::DeviceKind::Nmos, std::schematic::signals(4), <args>, x=…, y=…);` |
| `connect(cell, a, b, route)` | `std::schematic::connect(a, b, route=[…]);` |
| `add_symbol_items(cell, items)` | One `std::symbol::…;` statement per item: a shape, a text, or a pin. |
| `create_symbol(cell)` | Writes the cell's generated box (§4.1) as `std::symbol` statements, from `generated_box` on the published compile, with `label=true` on each pin in place of the pin names. It refuses when the cell already draws a symbol, or when a port has no path (§3.4), and names those ports. |
| `delete(targets)` | Deletes elements, connections, and symbol items as §6.5 describes, or refuses and lists the references that block it. |
| `place(edits)` | Moves, rotates, and mirrors elements and rewrites routes, including Fix positions, segment drags, and Remove Route. It reuses the implementation of `update_values`, with `x`, `y`, `angle`, `reflect`, and `route` as the keywords. | `call_arguments(call)` | Returns the source text of a call's arguments, for the properties panel. |

- **Placement rides along.** `add_signal` and `connect` also take placement edits for other calls and apply them in the same `WorkspaceEdit`. The wire tool uses this to fix the positions of the unplaced elements it touches (§4.2).
- **Selection** reuses `select_rect`, renamed to `select_span`.
- **The GUI's wrappers for these methods are async.** `call_async` (`gui/src/rpc.rs:181`) becomes `pub(crate)`, and `select_span` and `place` get async wrappers instead of the blocking ones that `select_rect` and `update_values` use today.

### 6.5 Edit builders

These live in a new `crates/analyzer/src/schematic_edit.rs`.

- **Statement text** uses full paths and no imports. Tests check it in the style of `assert_compiles_without_imports` (`rpc.rs:1245`).
- **Fresh names.**
  - Instances are named after their cell plus a number (`mos0`).
  - Devices are named after their kind plus a number (`nmos0`, `res0`), and the netlist names them after that binding (`Mnmos0`, `Rres0`, §2.3).
  - Generated names are unique among the root scope's bindings.
  - User-typed names pass the identifier and keyword checks of `validate_cell_name` and must not shadow an existing binding.
- **`pub let` vs `let`.** Ports, instances, and devices get `pub let`, as the layout tools do. Net labels get plain `let`, which means bypassing `let_prefix`: it returns `pub let` for any statement at a cell's top level.
- **Deletion.** No delete helper exists yet. The new one works like this:
  1. Only a statement of the form `let x = <call>;` or `<call>;` can be deleted. An element created inside a larger statement, such as one signal of `pub let data = [Signal(), Signal()]`, can't be deleted from the GUI.
  2. The navigation index finds the binding's references.
  3. Some references are cleaned up along with the element:
     - `connect` statements in the cell body are deleted;
     - an element of a device's literal terminal list is replaced with `std::schematic::Signal()`.
  4. Any other reference blocks the deletion:
     - another `let`;
     - a struct literal;
     - a `connect` in a loop or function;
     - a parent reading the field through an instance, possibly in another file.

     The GUI lists the blocking references and can reveal each one.
  5. Each statement is removed together with its line when nothing else is on it, and the edits are sorted by descending offset.
- **Symbol statements.**
  - `Float` literals are written with the fewest digits that read back as the same value, and always with a `.`: `2.`, `-0.25`.
  - Keywords at their defaults (`fill=false`, `size=1.`, `align=std::symbol::Align::Left`) are left out.
  - `pin` names its port by its path (§3.4), as `connect` names a terminal.
  - `param` writes the parameter's name as both the label and the value, as in `param("w", w, …)`. The builder checks that the name still resolves to the cell's parameter at the end of the body.
- **Deleting symbol items.** A `std::symbol` call returns `()`, so nothing refers to it, and step 5 removes its statement. A group is deleted by removing the statement of its origin.
- **Shared helpers.**
  - `let_prefix` becomes `pub(crate)`.
  - `missing_initial_condition_edit` (`rpc.rs:390`) is generalized into an "ensure keyword" helper that `set_argument` uses.

| Delete | Deletes the statement, or for a group, its origin's statement. |

**Stretching.** Moves, rotations, and segment drags rewrite routes in the same edit, so wires stay orthogonal:

- When a pin moves, the corner next to it follows the move's vertical part if the end segment is horizontal, or its horizontal part if that segment is vertical. The end segment keeps its direction, and the next one stretches.
- A wire without corners gets one, and so does an end segment that's already diagonal.
- A wire whose ends both move, such as one between two selected elements, moves with them.
- Dragging a segment sideways moves the corners at both its ends, and adds a corner where it ends at a pin.
- Locked routes aren't rewritten, so their ends just follow the pins.

## 11. Risks

- **Stale edits.** A gesture computed from an old snapshot could edit the wrong code. The checks in §6.1 refuse it.
- **A breaking change.** Reserved device keywords break code that passes `x`, `y`, `angle`, or `reflect` as parameters. These names are unlikely in device models, and the docs will say so.
- **The `Ty::Device` change is broad.** It touches field access, detached reads, and cell-parameter checks. To contain it, `Device` is a single kind-erased type that follows `SchematicInst` everywhere, and it lands in milestone 2 with focused tests.
- **Hand-written code has no wires.** Its schematics show symbols in slots joined by flylines until someone draws wires. Placing elements, adding labels, and wiring flylines in the GUI (§4.4) turn them into drawings.
- **Pin positions are a source format.** Stored routes end at pins, so anything that moves a pin moves wire ends. For example, a child cell with a generated box that gains a port reshapes its box, and a pin dragged in the symbol view moves in every parent. The parents' wires stay attached and can turn diagonal, and dragging the element straightens them. The rules in §4.1 are fixed for this reason. Create Symbol writes the box's pins exactly, so drawing a symbol can start without moving any pin. Rewriting the routes in every parent when a pin moves is not planned.
- **A pin is required for every port.** Adding a port to a cell that draws a symbol is an error until the port gets a pin. The error points at the new port, and the pin tool picks it first.
- **Device symbols are compiled.** `device_symbol` compiles internal cells once per process. A helper that fails to compile would leave raw devices without symbols, so a test builds every kind and terminal count.
- **`DeviceKind` gains variants.** A `match` on `DeviceKind` that lists every variant without a wildcard arm stops compiling.
- **Misleading drawings.** Wires don't connect, so a drawing could look connected where the netlist isn't, or the reverse. Conflict markers (§4.3) and flylines (§4.4) show both cases.
- **Generated elements and wires can't be edited one by one.** Code can still position and route them (`x=4 * i`, `route=[(4 * i, 6)]`), and a later per-element statement could help (§12).
- **The UI thread can block.** Every new wrapper is async.
- **`LayoutCanvas` is coupled to the rest of the GUI.** Only the sites in §5.1 change, and only the pure camera math moves out of it.
- **Large generated schematics.** Paths share storage, the scene is built in a background task, painting culls to the viewport, and flylines can be hidden.
- **Recompile scope.** A placement, route, or symbol edit in a child recompiles its ancestors and re-sends them, because `CellId` folds in what a cell refers to. That's the same as any other edit to the child.

## 12. Not planned

- Wires that connect by touching. Only `connect` and terminal lists connect, so the compiler never needs pin positions.
- Automatic wiring. The GUI never routes a connection by itself. A later command could compute a route and write it to source like any other.
- Placing elements created in loops and functions one by one. A later `std::schematic::place(element, x=…, y=…)` statement could position them by path. Keywords on the creating call stay the main mechanism, because deleting the statement also deletes the placement.
- Junctions that split a wire's `connect` where another wire branches from it. A branch repeats the other wire's corners instead (§4.3), so it never rewrites an existing statement.
- Several pins for one port. Routes would have to say which pin they end at.
- Rewriting parents' routes when a pin moves. A later gesture could find the parents through the navigation index, and that edit would touch several files.
- Line styles, colors, widths, and rotated text in symbols.
- Cross-probing between layout and schematic. Nothing links a cell's layout instances to its schematic instances today.
- Simulation and testbenches.
- Layout generated from the schematic.
- Multi-sheet schematics and off-page connectors.
