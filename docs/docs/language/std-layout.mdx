# `std::layout`

`std::layout` is the standard library module that builds layout: geometry constructors, instance placement, bounding boxes, routing, vias, dimensions, and helpers for working with rectangles and for symmetric layout.

## Importing

Nothing in `std::layout` is in scope by default. Import the names a module calls with a grouped `use` at the top of the file:

```argon
use std::layout::{crect, inst, rect};

cell pad(w: Float, h: Float) {
    pub let metal = rect("met1", x0=0., y0=0., w=w, h=h);
}

cell top() {
    let p = inst(pad(100., 80.), x=0., y=0.);
    let keepout = crect(x0=p.x - 20., y0=p.y - 20., w=140., h=120.);
}
```

A `use` applies only to the file that declares it, so each module imports what it calls. You can also call an item by its full path, as in `std::layout::rect("met1")`, import it under another name with `use std::layout::rect as r;`, or import the module with `use std::layout;` and call `layout::rect("met1")`. A module may declare its own item named `rect` or `inst`; to use the `std::layout` one as well, import it under an alias or call it by full path. See [imports](/language/modules-manifests#imports) for the full `use` syntax.

`rect`, `crect`, `polygon`, `path`, `text`, `inst`, `bbox`, `shapes`, `route_tracks`, and `dimension` are implemented by the compiler. They can only be called, so a reference that isn't a call, such as `let f = rect;`, is an error. The [placement helpers](#placement), [vias and rules](#vias-and-rules), [`autoroute`](#autoroute), the [rectangle helpers](#rectangle-helpers), and the [symmetry helpers](#symmetry) are ordinary Argon functions.

The examples below assume the names they call are imported. Signatures use the [built-in notation](/language/builtins#signature-notation).

## Placement

These place instances by their bounding boxes, and fix only the axis they arrange.

```argon
use std::layout::{column, inst, row};

cell bank() {
    let a = inst(unit(), x=0., y=0.);
    let b = inst(unit(), y=0.);
    let c = inst(unit(), y=0.);
    row([a, b, c], 200.);
}
```

## Routing

`autoroute` connects pins with wires on uniform tracks, keeps clear of obstacles and of other nets, and draws the result. It's an ordinary Argon function built on the native [`route_tracks`](#route-tracks), which does the routing and returns the geometry without drawing it.

```argon
use std::layout::{autoroute, crect, rect, RouteLayer, RouteNet, RoutePin, RouteVia};

cell top() {
    let a0 = rect("met1", x0=150., y0=950., x1=350., y1=1050.);
    let a1 = rect("met1", x0=1650., y0=950., x1=1850., y1=1050.);
    let b0 = rect("met2", x0=950., y0=150., x1=1050., y1=350.);
    let b1 = rect("met2", x0=950., y0=1650., x1=1050., y1=1850.);
    let wall = rect("met1", x0=900., y0=600., x1=1100., y1=1400.);
    let routed = autoroute(
        crect(x0=0., y0=0., x1=2000., y1=2000.),
        [
            RouteLayer { name: "met1", width: 100., space: 100., horizontal: true },
            RouteLayer { name: "met2", width: 100., space: 100., horizontal: false },
        ],
        [RouteVia { cut: "via1", size: 60., space: 60., bot_enc: (10., 20.), top_enc: (10., 20.) }],
        [[wall], []],
        [
            RouteNet { name: "a", pins: [RoutePin { layer: 0, rect: a0 }, RoutePin { layer: 0, rect: a1 }] },
            RouteNet { name: "b", pins: [RoutePin { layer: 1, rect: b0 }, RoutePin { layer: 1, rect: b1 }] },
        ],
    );
}
```

Net `a` climbs to `met2` to get past the wall and crosses `b` on `met1`. To route around a placed block, pass its metal as obstacles, for example `[shapes(blk, "met1"), shapes(blk, "met2")]`; an obstacle that touches pins of exactly one net counts as that net's metal, so a block's pins can be part of its shapes.

### `autoroute` {#autoroute}

<ApiItem id="autoroute" name="std::layout::autoroute" signature={'autoroute(area: Rect, layers: [RouteLayer], vias: [RouteVia], obstacles: [[Rect]], nets: [RouteNet]) -> [RoutedNet]'} summary={<>Routes nets between their pins and draws the wires, pin stubs, and vias.</>}>

<ParameterTable rows={[
  {name: 'area', type: 'Rect', typeHref: '/language/types/rect', requirement: 'Required, positional', description: 'The routing region. Its lower-left corner is a grid point, and routes use the grid points up to its upper and right edges.'},
  {name: 'layers', type: '[RouteLayer]', typeHref: '#route-layer', requirement: 'Required, positional', description: 'The routing layers, lowest first. Directions must alternate, and each pitch (width + space) must be a multiple of the first layer\'s.'},
  {name: 'vias', type: '[RouteVia]', typeHref: '#route-via', requirement: 'Required, positional', description: 'The via from each layer to the next: one fewer than there are layers.'},
  {name: 'obstacles', type: '[[Rect]]', typeHref: '/language/types/collections', requirement: 'Required, positional', description: 'obstacles[i] holds the obstacles on layers[i]. It may be shorter than layers.'},
  {name: 'nets', type: '[RouteNet]', typeHref: '#route-net', requirement: 'Required, positional', description: 'The nets to route, in order. Names must be distinct.'},
]} />

<Returns type="[RoutedNet]" href="#routed-net">One entry per net, in the order given, with the rectangles drawn for it.</Returns>

Grid points are spaced by the first layer's pitch in both directions, starting at the area's lower-left corner. Each layer's tracks are centered on every *n*th grid line, where *n* is its pitch divided by the first layer's, and its wires run along them. A wire on a track at the area's edge extends half a width past it.

A pin connects at the grid points whose wire ends it fully covers. A pin that covers none, such as one narrower than the wire or off the tracks, is extended to the nearest free grid point, and the extension is drawn on the pin's layer.

Each net's first pin is routed to each of its other pins in turn, joining the net's existing wires where that is shorter. Routing takes the shortest path in grid steps. If a net cannot be routed, routing starts over with that net first, or, if that order was already tried, from the net's next pin, up to 30 attempts in all.

For each pair of adjacent layers, [`max_via_array`](/language/builtins/vias#max_via_array) picks the cut array for two wires crossing, with each long enclosure along its layer's wires. Every via between the pair uses that array, centered on the crossing.

The router works in units of the technology's grid: widths, spacings, cut sizes, and enclosures must be multiples of it, and rectangle coordinates are snapped to it as drawn geometry is. Like an [`extern`](/language/extern-functions) call, it waits until every coordinate in its arguments is solved. The grid may have at most 4,000,000 points, summed over the layers.

Errors name the net and the pins: ``routing failed: net `b` has no route from pin 0 to pin 2`` when no attempt finds a route, and ``routing failed: pin 1 of net `b` has no free grid point nearby`` when everything around a pin is blocked. Invalid layers, vias, and pins are reported too, such as layers that do not alternate direction.

</ApiItem>

### Design rules {#route-design-rules}

On the routing layers, the result keeps these rules by construction:

- Wires are exactly the layer's width.
- Every wire, via landing, and pin stub is at least the layer's `space` from obstacles and from every other net's pins, wires, and vias. A gap of exactly `space` is allowed. The distance is measured separately in x and y, so the result is also legal under a rule that measures diagonally between corners.
- A gap narrower than `space` between two shapes of one net, such as via landings on neighboring tracks, is filled with metal, unless the fill would crowd another net.
- Via cuts and their enclosures are as `vias` gives them. Cuts of vias from different connections are at least the cut `space` apart. When one connection places two vias whose cuts crowd each other and whose landings are joined on both layers, the second via is dropped and its landings stay as metal.
- Different nets never touch, and each net's pins are connected.

It does not check:

- Minimum area: a short jog can leave a piece of metal smaller than the minimum.
- Rules that depend on wire width or length, such as wide-metal spacing and end-of-line spacing, and notch or step rules on the merged shape of a net.
- Spacing between cuts on different cut layers, such as stacked vias, and cut layers' obstacles, which `autoroute` does not take.
- Your own pins and obstacles: they are taken as legal. A fill may be narrower than the width where a wider one would crowd another net.
- Density and antenna rules.

## Vias and rules

These read the technology file's [design rules and vias](/language/technology#rules-and-vias), so a generator needn't hard-code a value or draw a contact array by hand.

```argon
use std::layout::{rect, rule, via, via_stack};

cell strap() {
    let li = rect("li1.drawing", x0=0., y0=0., x1=170., y1=1000.);
    let bar = rect("met1.drawing", x0=-100., y0=100., x1=270., y1=470.);
    via(li, bar);
    let wire = rect("met3.drawing", x0=-100., y0=100., x1=1000., y1=100. + rule("met3.width") + 100.);
    via_stack(bar, wire);
}
```

### `via` {#via}

<ApiItem id="via" name="std::layout::via" signature={'via(bot: Rect, top: Rect) -> Rect'} summary={<>Draws the largest array of cuts that fits where two shapes on adjacent layers overlap, with the enclosures the technology file requires.</>}>

<ParameterTable rows={[
  {name: 'bot', type: 'Rect', typeHref: '/language/types/rect', requirement: 'Required', description: <>The lower shape, such as an <code>li1.drawing</code> column.</>},
  {name: 'top', type: 'Rect', typeHref: '/language/types/rect', requirement: 'Required', description: <>The upper shape, such as a <code>met1.drawing</code> bar.</>},
]} />

<Returns type="Rect" href="/language/types/rect">The bounds of the cuts.</Returns>

The technology file's via from `bot`'s layer to `top`'s gives the cut layer, size, spacing, and the enclosure each shape needs, as a short side for every edge and a long side for two opposite edges. `via` tries both orientations of each enclosure, keeps the one with the most cuts, and centers the array on the grid. It waits until both shapes are placed. Shapes that don't overlap, layers no via joins, and an overlap too small for one cut are errors, and the last names the size one cut needs. It doesn't know about other shapes, so a contact to diffusion still has to keep clear of the gates (`licon.gate_space`), and a contact to poly needs nitride cut around it (`npc.licon_enclosure`).

</ApiItem>

### `via_stack` {#via-stack}

<ApiItem id="via-stack" name="std::layout::via_stack" signature={'via_stack(bot: Rect, top: Rect) -> [Rect]'} summary={<>Joins two shapes through every layer between theirs, with a via per layer and a pad on each layer in between.</>}>

<ParameterTable rows={[
  {name: 'bot', type: 'Rect', typeHref: '/language/types/rect', requirement: 'Required', description: 'The lower shape.'},
  {name: 'top', type: 'Rect', typeHref: '/language/types/rect', requirement: 'Required', description: 'The upper shape, any number of layers above.'},
]} />

<Returns type="[Rect]" href="/language/types/collections#sequences">The bounds of each via's cuts and each pad, from the bottom.</Returns>

The vias and pads stay within the shapes' overlap, except that a pad grows about its center to its layer's minimum width and area (`<layer>.width`, `<layer>.area`). Every via must fit in the overlap, so to start from a narrow shape, such as a 170-wide li1 column, draw a landing pad on the next layer and stack from that.

</ApiItem>

## Symmetry

Matched devices, such as a differential pair or a current mirror, match best when their layouts are mirror images or share a centroid. These helpers make both the easy path.

```argon
use std::layout::{eq_mirror, mirror_pair, rect};

cell pair() {
    let halves = mirror_pair(half(), 0.);
    eq(halves[0].x, -2000.);
    eq(halves[0].y, 0.);
    let left = rect("met2", x0=-900., x1=-600., y0=0., y1=2000.);
    eq_mirror(left, rect("met2"), 0.);
}
```
